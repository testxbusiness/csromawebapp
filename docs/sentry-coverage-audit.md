# Audit copertura Sentry — CSRoma WebApp

Data audit: 2026-11-01
Branch: `feat/sentry-observability`
Ambito: codice presente nel repository; nessun accesso o modifica a dati Supabase/Vercel.

## Esito sintetico

L’SDK Sentry è inizializzato in Browser, Node.js ed Edge; il test Preview ha confermato release, ambiente e mapping di uno stack trace al file TypeScript originale. Questo dimostra la catena di build/upload/source map, non la cattura uniforme degli errori applicativi.

Inventario rilevato: 73 file Route Handler, 108 funzioni HTTP esportate, nessuna Server Action identificata. Non esistono boundary `error.tsx` per segmento: è presente solo `global-error.tsx`. Nessun `captureException` esplicito è presente nelle Route Handler o nei servizi server. Quindi:

- errori che sfuggono al Route Handler e raggiungono Next.js sono coperti dal hook globale `onRequestError`;
- errori intercettati e convertiti in risposta HTTP (anche 500) non hanno una cattura Sentry garantita dal hook;
- `instrumentSupabaseClient` strumenta i client e le operazioni Supabase, ma un risultato `{ error }` gestito dal codice non equivale automaticamente a un evento di eccezione;
- errori non attesi di TanStack Query sono catturati dai callback globali della `QueryCache` e `MutationCache`, salvo errori HTTP numerici 4xx;
- l’evento è sanitizzato rimuovendo request, utente, server name, extra, tag, breadcrumb e messaggio libero. Questo protegge i dati, ma rende difficile attribuire gli eventi a una feature/operazione e costruire alert di funzione affidabili.

Gli alert qui proposti sono una policy iniziale: nel repository non risultano configurazioni Sentry Alert Rules, metric alert o monitor. La configurazione effettiva va verificata nel progetto Sentry.

**Disallineamento documentale:** la sezione “Remaining operational steps” in `docs/sentry-observability.md` afferma ancora che la configurazione Preview e la verifica source map sono da eseguire. Nel contesto di questo progetto sono già state completate e il deployment Preview di cleanup è stato verificato; resta da verificare nel pannello Sentry l’esistenza effettiva delle regole di alert e rimane separata l’approvazione del rilascio Production.

## Copertura trasversale verificata

| Superficie | Stato attuale | Limite / lacuna |
| --- | --- | --- |
| Browser | `src/instrumentation-client.ts`: SDK con `beforeSend`, ambiente/release, `tracesSampleRate: 0.1`, Replay a zero, `onRouterTransitionStart` | Gli errori gestiti localmente non arrivano necessariamente a Sentry; nessun tag funzionale persistente dopo la sanitizzazione |
| Node.js | `src/instrumentation.ts` importa `src/sentry.server.config.ts`; `onRequestError = Sentry.captureRequestError` | Copre gli errori di richiesta non gestiti; i `catch` che rispondono JSON devono catturare esplicitamente gli errori inattesi |
| Edge | `src/instrumentation.ts` importa `src/sentry.edge.config.ts`; stessa privacy e sample rate | Copertura delle eccezioni non gestite; nessun alert Edge specifico configurato |
| React/App Router | `src/app/global-error.tsx` chiama `captureException` | Boundary globale soltanto; mancano boundary segmentali e `not-found` dedicati. `global-error` non sostituisce la gestione errori nelle API |
| Route Handler | Hook Next globale e strumentazione client Supabase disponibili | Nessuna cattura esplicita per gli errori applicativi già gestiti; l’HTTP 500 restituito normalmente non è di per sé un’eccezione Sentry |
| Supabase SSR/browser/admin/recovery/middleware | `instrumentSupabaseClient` chiamato in tutte le factory individuate, incluso middleware | Le factory coprono i client, ma non classificano l’operazione/funzione; errori restituiti e assorbiti possono non diventare issue |
| TanStack Query | `QueryCache.onError` e `MutationCache.onError` fanno `captureException`; escludono 400–499 | Non distinguono feature/query key/mutation; il filtro non esclude `429`; l’errore può non avere status standardizzato |
| Source map/release | Preview ha mostrato `src/lib/sentry/preview-source-map-probe.ts:3` e release commit SHA | Verifica positiva per Node/server; mantenere verifica separata browser e release Production dopo l’approvazione |
| Privacy | `sanitizeSentryEvent` elimina identità, request, query/payload, tag e testo libero; Replay disabilitato | La perdita di tag impedisce breakdown/alert per `feature`, `operation` e route template. Valutare allowlist esplicita di soli valori costanti |
| Alert | Soglie iniziali documentate in `docs/sentry-observability.md` | Non verificabili dal codice; nessuna prova che siano state create nel progetto Sentry |

### Significato delle classi di alert nella mappa

- **P0 servizio/autenticazione** — pagina immediata se la disponibilità delle funzioni di login/sessione o delle API core scende: error rate server 5xx ≥5% per 5 minuti oppure ≥20 utenti colpiti in 5 minuti. Escludere credenziali errate e altri 4xx attesi.
- **P1 operazione critica** — notifica immediata se 5xx >1% per 15 minuti oppure ≥5 utenti colpiti in 30 minuti su operazioni finanziarie, mutazioni Athlete/Coach, messaggi o account admin. Non usare i soli 4xx di validazione/permesso.
- **P1 core** — stessa soglia per flussi principali di Athlete/Coach, autenticazione profilo, eventi e messaggi; separare le operazioni di scrittura dalle letture quando i tag allowlistati saranno disponibili.
- **P2 funzione secondaria** — digest lavorativo per ≥10 eventi inattesi in 24h o trend crescente a 7 giorni; include cataloghi/admin di consultazione, notifiche di test, standings e diagnostica non critica.
- **Escluso** — endpoint informativo di versione: monitorare solo errori di servizio inattesi aggregati, senza alert per singolo evento.

## Lacune prioritarie e piano raccomandato

1. **P1 — Rendere osservabili gli errori applicativi gestiti.** Nei `catch` delle API catturare solo errori inattesi prima di restituire 5xx; non inviare validazioni, auth deny, not found o conflitti previsti. Usare un helper server con `captureException` e un fingerprint stabile per feature/operazione, senza includere ID, URL/query, payload o testo utente.
2. **P1 — Rendere gli alert attribuibili senza dati personali.** Definire tag allowlistati costanti (`feature`, `operation`, `runtime`, `status_class`, eventualmente `route_template` senza parametri). Aggiornare la sanitizzazione per conservarli solo se appartengono a enumerazioni note. Non conservare URL o parametri.
3. **P1 — Errori Supabase gestiti.** Aggiungere un wrapper che converta gli errori inattesi restituiti da Supabase in un’eccezione sanitizzata con codice/classe operazione non sensibile; escludere esplicitamente auth/permission/validation e risposte attese. Non inviare query, messaggi DB, nomi/tabelle contenenti dati personali o valori.
4. **P1 — Finanza e mutazioni amministrative.** Separare errori di scrittura per pagamento/incasso, quote, rate e correzioni da errori di lettura; soglia P1 e tag operazione stabili. La copertura Sentry non sostituisce audit log o controlli transazionali.
5. **P1 — Query/mutation client.** Aggiungere classificazione allowlistata di feature e operation ai callback globali; uniformare l’estrazione status (incluso `Response.status`) e decidere il trattamento di 429/rate limit. Lasciare gli errori attesi nella UI senza inviarli.
6. **P2 — Boundary segmentali.** Aggiungere `error.tsx` ai gruppi/aree che devono mostrare fallback locale e conservare route/contesto utente; lasciare il capture esplicito una sola volta per evitare duplicati con cattura automatica.
7. **P2 — Health check e PWA.** Tracciare senza contenuto personale errori di registrazione/aggiornamento service worker, push subscription e offline fallback; distinguere supporto non disponibile o permesso negato da malfunzionamento inatteso.
8. **P2 — Verifica alert Sentry.** Creare e provare le regole nel progetto Sentry separando `environment=production` da Preview. Le soglie sono in `docs/sentry-observability.md`; Preview deve restare non-paginante.
